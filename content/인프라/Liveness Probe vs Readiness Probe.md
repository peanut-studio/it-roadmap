# Liveness Probe vs Readiness Probe (살아있음 검사와 준비됨 검사)

## 📝 정의

컨테이너를 재시작할지 트래픽만 끊을지를 가르는 **두 검사**다.

kubelet 은 컨테이너마다 정해진 주기로 안쪽을 두드려 본다. **두드리는 방법은 둘이 같고, 갈리는 것은 실패했을 때 하는 일이다.** 살아있음 검사가 실패하면 컨테이너를 죽여 다시 띄우고, 준비됨 검사가 실패하면 트래픽만 끊고 죽이지는 않는다. 그래서 손이 가는 곳은 어느 검사를 걸지가 아니라 각 검사 안에 무엇을 넣을지다.

### 이름
Live :: 살아 있다
-ness :: 그 상태
Ready :: 받을 준비가 됐다
Probe :: 찔러 보는 검사
= 붙여 읽으면 "살아 있나 찔러 보기" 와 "이제 받아도 되나 찔러 보기". 묻는 것부터가 다르다

### 비유
몸살이 났냐고 묻는 것과 오늘 손님을 받을 수 있냐고 묻는 것 — 앞의 물음에 옆 가게 사정까지 끼워 넣으면 멀쩡한 가게가 문을 닫는다.

### 예
파드 목록을 띄웠는데 재시작 횟수만 혼자 계속 올라가고 있던 그 화면이다.

## 🖼️ 그림으로 보기

```도해
대조: 두 검사 안에는 각각 무엇까지 넣어야 하나
살아있음 검사 |=| 준비됨 검사
묻는 것 :: 스스로 못 빠져나오나 || 지금 받아도 되나
밖에 매달린 것 :: 넣지 않는다 || 넣어도 된다
잘못 넣으면 :: 남의 고장에 내가 죽는다 || 잠깐 줄에서 빠질 뿐
= 실패했을 때 하는 일이 다르니, 안에 담을 물음도 달라야 한다
```

## ⚠️ 해결하는 문제

```도해
대조: 살아있음 검사 안에 DB 확인 한 줄을 넣으면 무슨 일이 생기나
넣으면 || 안 넣으면
DB 가 5초 느려짐 :: 파드가 전부 재시작 || 파드는 그대로 돈다
그다음 :: DB 를 더 누른다 || 회복을 기다린다
고장 범위 :: 한 곳에서 전체로 번진다 || 고장 난 곳에 머문다
= 살아있음 검사에 적어 넣은 것은 곧 내 컨테이너를 죽이는 스위치가 된다
```

검사에 무엇을 넣을지는 취향 문제가 아니다. 살아있음 검사가 실패하면 kubelet 이 컨테이너를 죽이므로, **그 검사 경로가 건드리는 모든 것이 내 컨테이너를 죽일 수 있는 스위치**가 된다. 확인 경로에 DB 조회 한 줄을 끼워 두면 DB 가 5초 느려진 날 멀쩡한 앱이 전부 재시작되고, 한꺼번에 다시 뜬 파드가 도로 접속을 몰아 DB 를 더 누른다. 한 곳의 고장이 전체 정지로 번지는 길이 이렇게 생긴다.

준비됨 검사는 똑같은 것을 확인해도 결과가 다르다. 실패하면 파드가 받는 목록에서만 빠지고 컨테이너는 계속 돌기 때문에, DB 가 돌아오면 다음 검사에서 곧바로 목록에 되돌아온다. 그래서 **밖에 매달린 것은 준비됨 검사에, 안에서 스스로 못 빠져나오는 상태만 살아있음 검사에** 넣는 것이 규칙이 된다. 마이크로소프트의 아키텍처 문서도 확인 한 번에 이것저것 다 물리면 앱이 멀쩡한데도 못 쓴다고 판정된다며, 확인 경로를 중요도별로 나눠 열라고 적는다.

## ⚙️ 작동 원리

두드리는 방법은 넷이고 두 검사가 똑같이 쓴다 — 안에서 명령을 실행해 종료 코드 0 을 보거나, HTTP GET 을 던져 200~399 를 받거나, TCP 포트를 열어 보거나, gRPC 상태가 SERVING 인지 묻는다. 늦게 뜨는 앱을 위한 셋째 검사(startup)도 같은 넷을 쓰고, 실패하면 살아있음 검사와 똑같이 컨테이너를 죽인다.

두 검사는 손잡이도 같이 쓴다. `initialDelaySeconds`(첫 검사까지 기다릴 초, 기본 0), `periodSeconds`(검사 주기, 기본 10초), `timeoutSeconds`(응답을 기다릴 초, 기본 1초), `failureThreshold`(연속 몇 번 실패하면 판정할지, 기본 3), `successThreshold`(다시 성공으로 돌리는 데 필요한 연속 성공 수, 기본 1).

여기서 앞 절의 규칙이 숫자로 다시 나타난다. **응답을 기다리는 기본값이 1초**다. 확인 경로를 밖에 매달린 것까지 다녀오게 만들어 두면 앱이 멀쩡한 날에도 검사만 1초를 넘겨 실패하고, 그게 살아있음 검사면 그 순간 컨테이너가 죽는다. 검사 경로를 좁게 두라는 말은 이 1초에서 나온다.

판정까지 걸리는 시간은 `failureThreshold × periodSeconds` 이라 기본값이면 30초쯤이다. 기동이 3분 걸리는 앱에 살아있음 검사를 그냥 걸면 30초마다 죽고 다시 뜨는 무한 고리에 들어가고, 이때 쓰라고 startup 검사가 있다 — `failureThreshold: 30 · periodSeconds: 10` 이면 5분까지 봐준다.

실패했을 때 터미널에서 보는 것은 파드 상세의 이벤트 두 줄이다. 이 두 줄이 있으면 앱이 스스로 죽은 게 아니라 **kubelet 이 죽인 것**이다.

```text
Warning  Unhealthy  10s (x3 over 20s)  kubelet, node01  Liveness probe failed: cat: can't open '/tmp/healthy': No such file or directory
Normal   Killing    10s                kubelet, node01  Container liveness failed liveness probe, will be restarted
```

## 💡 실제 사례

- **배포 중 502** — 준비됨 검사 없이 올리면 아직 못 받는 파드가 목록에 먼저 들어가 앞단이 그리로 보낸다.
- **DB 가 5초 느려진 날** — 살아있음 검사가 DB 까지 확인하면 멀쩡한 앱이 전부 재시작되고, 한꺼번에 다시 뜬 파드가 DB 를 더 누른다.
- **확인 경로가 무거운 앱** — 검사 한 번이 여기저기를 모아 오면, 부하가 몰린 순간 앱보다 검사가 먼저 1초를 넘긴다. 장애를 만드는 것이 앱이 아니라 검사다.

## 🚫 흔한 오해

- **둘 다 걸어 두면 안전하다** — 무엇을 확인하느냐가 문제다. 살아있음 검사 안에서 밖에 매달린 것까지 확인하면, 남의 고장이 내 컨테이너를 죽이는 스위치가 된다.
- **준비됨 검사가 실패하면 파드가 재시작된다** — 아니다. 목록에서 빠질 뿐 컨테이너는 그대로 돌고, 다시 성공하면 목록에 되돌아온다.
- **살아있음 검사를 촘촘히 걸수록 빨리 회복한다** — 쿠버네티스 문서 자체가 이걸 경고한다. 잠깐 몰린 부하로 검사가 밀리면 kubelet 이 죽이고, 남은 파드에 부하가 더 몰려 연쇄로 번진다.

## 🚨 주의사항

- **살아있음 검사는 가장 좁게 만든다.** 그 안에서 다른 곳에 물어보지 않는다. "이 안에서 스스로 못 빠져나오는 상태인가" 만 본다.
- **준비됨 검사는 넉넉히 봐도 된다.** 여기서 밖에 매달린 것을 확인하면 그 앱만 조용히 줄에서 빠지고 끝난다.
- **`timeoutSeconds` 기본값 1초를 확인해라.** 검사 경로가 1초 안에 못 끝나면 앱은 멀쩡한데 검사만 계속 실패한다.
- **종료할 때 순서가 있다.** 목록에서 빠지고 나서도 이미 들어온 것을 마저 처리해야 하므로 [[Graceful Shutdown]] 과 짝으로 본다.

## 📝 정리

**"살아있음 검사에 적어 넣은 것은 전부 내 앱을 죽이는 스위치다"** 라고 읽으면 된다. 두 검사는 두드리는 방법이 같고 실패했을 때 하는 일만 다른데(하나는 죽이고 하나는 목록에서만 뺀다), 그 차이 때문에 안에 담을 물음도 달라져야 한다. 밖에 매달린 것은 준비됨 검사에 넣어 조용히 줄에서 빠지게 하고, 살아있음 검사에는 안에서 스스로 못 빠져나오는 상태만 남긴다.

## 🧒 열 살에게

몸이 아픈 것과 친구가 안 와서 못 노는 것은 다르잖아. 아픈 애는 집에 보내야 하지만, 친구를 기다리는 애까지 집에 보내면 아무 잘못 없는 애가 쫓겨나는 거야. 그래서 아프냐고 물을 땐 그 애 몸만 물어야지, 친구가 왔는지까지 같이 물으면 안 돼.

## ❓ 이해했는지

- DB 가 잠깐 느려진 날 앱 파드가 전부 재시작되는 사고는 어디서 시작되나 → 해결하는 문제
- 앱은 멀쩡한데 검사만 계속 실패하는 일은 왜 생기나 → 작동 원리
- 밖에 매달린 것을 확인해도 되는 검사는 어느 쪽이고 왜 그런가 → 그림

## 🔗 관련 용어

- [[Pod]] — 두 검사가 실제로 걸리는 자리
