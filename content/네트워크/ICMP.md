# ICMP (Internet Control Message Protocol)

## 📝 정의

ICMP는 **데이터를 나르지 않고 문제가 생겼다고 알리는 프로토콜**이다.

이름 가운데의 Control Message 가 정체다 — 내용물이 아니라 통제 메시지를 나른다. IP 는 보낸 것이 닿았는지 알려주지 않아서, 중간에서 버려진 패킷은 아무 소리 없이 사라진다. 그 침묵을 깨라고 만든 것이 ICMP 이고, RFC 792 는 모든 IP 모듈이 이것을 반드시 구현해야 한다고 못 박았다.

### 이름
Internet :: 이어 붙인 망
Control :: 통제하는
Message :: 전갈
Protocol :: 약속
= 붙여 읽으면 "망을 통제하는 전갈을 나르는 약속". 짐이 아니라 전갈만 나른다

### 비유
반송된 우편물에 붙은 쪽지 — 편지를 대신 배달해주지는 않고 왜 못 갔는지만 적혀 있다.

### 예
인터넷이 답답할 때 터미널에 ping 을 쳐 보면 돌아오는 그 한 줄이 이 메시지다.

### 직접
명령 창에서 `ping google.com` 을 쳐 보라. 줄마다 찍히는 왕복 시간이 이 전갈이 갔다 온 시간이다.

## 🖼️ 그림으로 보기

```도해
흐름: 보낸 패킷이 중간에서 버려지면 무엇이 돌아오나
보낸 쪽 :: 목적지로 IP 패킷을 띄운다
라우터 :: 넘기려는데 길이 없거나 TTL 이 0 이다
라우터 :: 그 패킷을 버린다. IP 는 여기서 조용하다
< 라우터 :: 버린 사유를 ICMP 로 보낸 쪽에 알린다
< 보낸 쪽 :: 데이터는 못 갔고 사유만 손에 남는다
= 짐은 사라지고 사유서만 돌아온다 — ICMP 가 나르는 것은 그것뿐이다
```

## ⚠️ 해결하는 문제

```도해
대조: 실패를 알려주는 장치가 없으면 어떻게 되나
ICMP 없이 || ICMP 로
버려진 패킷 :: 아무도 모른다 || 사유가 돌아온다
원인 찾기 :: 전 구간을 뒤진다 || 어느 홉인지 나온다
살았는지 :: 보내봐야 안다 || 물어보면 답한다
= 실패를 소리 내게 만드는 것, 그것이 ICMP 가 하는 일이다
```

IP 는 최선을 다해 옮겨보고 안 되면 버린다. 버렸다는 사실을 아무도 기록하지 않으면, 연결이 안 될 때 볼 수 있는 것은 "응답이 없다" 뿐이다. 회선이 끊긴 것인지, 주소가 없는 것인지, 몇 번째 라우터에서 막힌 것인지 구별할 방법이 없다.

ICMP 는 버린 쪽이 **버린 사유를 보낸 쪽으로 되돌려 보내게** 만든다. 다만 RFC 792 가 함께 적어둔 단서가 있다 — 이 메시지들의 목적은 통신 환경의 문제를 알리는 것이지 IP 를 신뢰성 있게 만드는 것이 아니다. 무한히 되물리는 것을 막으려고 ICMP 에 대해서는 ICMP 를 보내지 않는다.

## ⚙️ 작동 원리

```도해
흐름: traceroute 는 어떻게 중간 라우터들의 이름을 알아내나
보낸 쪽 :: TTL 을 1 로 박아 첫 패킷을 띄운다
첫 라우터 :: TTL 이 0 이 되니 버릴 수밖에 없다
< 첫 라우터 :: 시간 초과 ICMP 를 돌려주며 자기를 드러낸다
@ TTL 올리기 :: 2, 3, 4 … 목적지가 에코 응답을 줄 때까지
= 일부러 시간을 초과시켜, 실패 신고를 경로 지도로 바꾼다
```

TTL(Time To Live)은 이름과 달리 시간이 아니라 **지날 수 있는 라우터 수**를 센다. 라우터는 넘기기 전에 이 값을 최소 1 씩 깎고, 0 이 된 패킷은 버린 뒤 시간 초과 ICMP 를 되돌려 보낸다. traceroute 는 이 규칙을 도구로 쓴다.

ping 은 더 단순하다. 에코 요청을 보내고 에코 응답이 오는지를 본다. 확인되는 것은 딱 거기까지 — IP 수준의 연결이다.

| 타입 | 이름 | 언제 오나 |
|---|---|---|
| `0` | Echo Reply | 살아 있다는 답 |
| `3` | Destination Unreachable | 갈 길이 없다 |
| `8` | Echo | 살아 있냐고 묻기 |
| `11` | Time Exceeded | TTL 이 0 이 됐다 |

## 💡 실제 사례

- **살았는지 물어보기** — ping 이 에코 요청을 보내고 에코 응답이 오는지 본다. 왕복 시간이 함께 찍힌다.
- **어디서 막혔는지 찾기** — traceroute 가 TTL 을 1 부터 올려가며, 홉마다 돌아오는 시간 초과 신고를 모아 경로를 그린다.
- **큰 패킷이 사라질 때** — 조각내지 말라는 표시를 켜고 ping 을 보내면, 경로 MTU 문제가 신고로 드러난다.

## 🚫 흔한 오해

- **ping 이 안 되면 서버가 죽은 것이다** — ICMP 를 막아둔 장비는 멀쩡해도 답하지 않는다. traceroute 에 별표가 뜨는 것도 그 라우터가 죽어서가 아니라 시간 초과 신고를 안 돌려주기 때문이다.
- **ping 이 되면 그 서비스도 되는 것이다** — ping 이 확인하는 것은 IP 수준의 연결까지다. 그 위에서 도는 웹 서버가 멈춰 있어도 에코 응답은 잘 돌아온다.
- **ICMP 가 있으니 빠진 패킷은 다시 보내진다** — 사유서만 돌아온다. 다시 보내는 일은 TCP 가 하고, ICMP 는 IP 를 신뢰성 있게 만들지 않는다.

## 🚨 주의사항

- **ICMP 를 통째로 막으면 진단이 눈을 잃는다.** 경로 MTU 문제를 알려주던 신고까지 함께 막혀서, 큰 패킷이 어디서 사라지는지 알아낼 길이 없어진다.
- **traceroute 의 별표를 장애로 읽지 않는다.** 그 홉이 신고를 안 돌려주면 별표가 찍힐 뿐이고, 아래 홉들이 정상으로 이어지면 경로는 살아 있다.

## 📝 정리

**"짐 대신 사유서만 돌아오는 그 약속"** 이라고 읽으면 된다. ping 과 traceroute 는 그 신고를 일부러 만들어내서 읽는 도구다. 신고가 왔다고 잃어버린 패킷이 되살아나지는 않는다.

## 🧒 열 살에게

편지를 부쳤는데 며칠 뒤 "주소가 없어요" 쪽지만 붙어서 되돌아온 적 있지? 그 쪽지는 편지를 대신 갖다 주지는 않고, 왜 못 갔는지만 알려 줘. 인터넷에도 그런 쪽지가 있어서, 안 될 때 그냥 깜깜한 게 아니라 까닭을 알 수 있어.

## ❓ 이해했는지

- traceroute 가 중간 라우터의 이름을 어떻게 알아내나 → 작동 원리
- ping 은 되는데 웹페이지는 안 열리는 일이 왜 생기나 → 흔한 오해
- 라우터가 패킷을 버렸을 때 원래 데이터는 어떻게 되나 → 그림
