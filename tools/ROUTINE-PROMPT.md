# 자동 단어 수집 루틴 프롬프트

**이 파일이 프롬프트다.** 클라우드 루틴 3개가 실행 첫머리에 이 파일을 읽는다.

등록된 트리거에는 한 줄만 들어 있다:

> 저장소의 `tools/ROUTINE-PROMPT.md` 를 읽고 그 지시를 그대로 따르라.
> 이번 실행의 전략은 **`<전략 이름>`** 이다.

프롬프트를 트리거에 박아 두지 않는 이유: 박아 두면 고칠 때마다 API 를 불러야 하고,
무엇이 고쳐졌는지 git 에 남지 않는다. 실제로 첫 실행에서 이 파일의 지시 하나가
검사기와 어긋나 있는 것이 드러났다 — 파일이면 커밋 한 번으로 끝난다.

| 루틴 | 전략 이름 | 시각 | cron (UTC) |
|---|---|---|---|
| `vocab-roadmap` | 표준 로드맵 빈칸 | 월 00:00 KST | `0 15 * * 0` |
| `vocab-trend` | 최신 실무 용어 | 수 00:00 KST | `0 15 * * 2` |
| `vocab-related` | 관련 용어 따라가기 | 금 00:00 KST | `0 15 * * 4` |

아래 **공통 본문**을 따르고, 자기 전략에 해당하는 문단만 2번 단계에 적용한다.
삭제는 https://claude.ai/code/routines 에서.

## 절대 어기면 안 되는 것

1. **추가만 한다.** 기존 파일을 수정·이동·개명·삭제하지 마라.
   단어 id 는 "{권}--{제목slug}" 이고 그게 사용자 학습 기록의 열쇠다.
   파일을 옮기면 권이 바뀌고 id 가 바뀌어 그 사람의 진도가 사라진다.
   분류가 어색해 보여도 고치지 마라. 그건 사람이 할 일이다.
2. **새 폴더를 만들지 마라.** 위 목록의 폴더에만 쓴다. content/ 루트에도 쓰지 마라.
3. **tools/ 와 docs/ 를 고치지 마라.** BOOKS, 템플릿, 허용 출처 목록 전부 읽기만 한다.
4. **회당 2개.** 더 많이 넣지 마라.
5. 대상 권의 단어가 이미 **60개 이상**이면 그 권에는 추가하지 말고 다른 권을 골라라.
   상한을 숫자로 두는 이유는 한 권만 부풀지 않게 하려는 것이다. 12권이 다 상한에
   닿으면 루틴이 매번 빈손으로 끝나므로, 그때는 사람이 상한을 다시 본다.

## 순서

### 1. 현황 파악

    python3 tools/build.py --dry-run

권별 단어 수를 기록해 둔다. 실행 기록에 넣어야 한다.
content/ 를 훑어 기존 단어 목록을 확보한다. 파일명이 대체로 단어 이름이지만
판정 기준은 H1 제목이다(아래 3번 참조).

### 2. 후보 고르기

**이 문서 맨 아래 「전략별 문단」에서 네 전략에 해당하는 것만 읽고 따르라.**

### 3. 중복 배제 — 세 축을 모두 본다

파일명만 보면 놓친다. build.py 는 H1 제목으로 중복을 판정하고, 제목이 겹치면
한쪽을 조용히 버린다. 다음 셋을 정규화해서 대조해라.

  - 파일명
  - H1 제목 (예: "# DNS (Domain Name System)" 의 "DNS")
  - 괄호 안 원어 (위 예의 "Domain Name System")

정규화: 대소문자 무시, 공백/하이픈 무시, 한영 표기(로드 밸런서 = Load Balancer),
약어 확장(CDN = Content Delivery Network) 을 같은 것으로 본다.

또 하나: 제목의 slug 가 같은 권의 기존 slug 와 부딪히면 그 후보를 버려라.
부딪히면 기존 단어의 id 를 빼앗아 남의 진도가 엉뚱한 단어에 붙는다.

권 이름만 보고 "여기 없겠지" 하고 판단하지 마라. 실제로 grep 해라.
예를 들어 WebSocket 은 web 이 아니라 content/네트워크/ 에 있고,
Sharding 은 db 가 아니라 content/아키텍처/ 에 있다.

### 4. 출처 조사 — 1차 출처만

tools/sources.allowlist.md 를 읽어라. 거기 있는 도메인만 인용할 수 있다.
표준 문서(RFC, W3C, WHATWG), MDN, OWASP, 프로젝트 공식 문서, 클라우드 공식
문서만이다. 블로그·튜토리얼·백과사전·Q&A 는 안 된다.

단어마다 **서로 다른 도메인의 출처 2개 이상**을 실제로 읽어라. 못 채우면
그 후보를 버리고 다른 것을 골라라. 기억으로 쓰지 마라 — 반드시 원문을 열어라.

### 5. 집필

먼저 이 셋을 읽어라. 형식은 여기서 배운다:

    docs/TERM-TEMPLATE.md          규약
    content/네트워크/DNS.md         본보기 (도해 세 종류를 다 쓴다)
    content/네트워크/HTTP.md        본보기

규칙을 요약해서 외우려 하지 마라. tools/check_template.py 가 판정하고 그
검사기는 계속 강화된다. 템플릿 문서를 읽고 본보기를 따라 써라.

특히 주의할 것:
  - `🖼️ 그림으로 보기` 는 필수다. ```도해 블록 하나만 들어가고 글은 안 된다.
    이 자리에는 흐름·대조·층 **어느 모양이든** 올 수 있다. 흐름이 기본값이 아니다.
    판정법: 그 그림만 보고 정의 첫 문장이 복원되면 맞는 그림이다.
  - 도해는 흐름/대조/층 세 종류이고 첫 줄이 "모양: 질문" 이며 제목은 물음이어야 한다.
  - 도해 마지막의 "= 한 줄 결론" 은 필수다.
  - `<` 는 **응답이 실제로 돌아오는 자리**에만 쓴다. 앱이 그 앞에
    "여기서부터 돌아오는 길" 을 새기기 때문에, 아무것도 안 돌아오면 그림이 거짓말을 한다.
    처음으로 되돌아가는 순환이면 `<` 가 아니라 `@` 다.
  - `@ 이름 :: 하는 일` 은 한 바퀴 도는 흐름의 **마지막 줄**에만 쓴다.
    이벤트 루프·에이전트 루프·Circuit Breaker 처럼 돌고 도는 개념을 직선으로 펴지 마라.
    상태 전이(닫힘→열림→반열림)도 층이 아니라 `@` 흐름이다.
  - 대조의 칸 이름 줄에 `|=|` 를 쓰면 ✕/✓ 없이 양쪽이 같은 색으로 선다.
    **왼쪽 칸에 장점이 한 줄이라도 있으면 `||` 가 아니라 `|=|` 다.** 세션 vs JWT 처럼
    둘 다 정당한 선택은 `|=|`, 캐시 없이 vs 캐시로처럼 한쪽이 실제로 나쁘면 `||`.
  - `❓ 이해했는지` 의 질문 3개는 전부 `- 질문 → 답이 있는 자리` 형식이다.
    화살표 뒤에는 **이 노트에 실재하는 섹션 이름**을 쓴다(그림 도해면 `그림`).
    화살표를 못 달겠으면 답이 노트에 없다는 뜻이니 질문을 바꾸거나 내용을 채워라.
  - `💡 실제 사례` 의 각 항목은 `- **상황** — 설명` 이다. `— ` 를 빠뜨리지 마라.
  - `🚫 흔한 오해` 중 하나는 대안이 있는 기술이면 **과잉 적용**(X 가 항상 낫다)을 겨눈다.
  - 노트 밖에서 배워야 하는 용어는 반 구절로 풀거나(`벡터(뜻을 담은 숫자 목록)`)
    `[[링크]]` 를 걸고 🔗 관련 용어에 올려라. 본문 `[[링크]]` 는 앱에서 누를 수 있다.
  - 정의의 첫 문단은 정확히 한 문장, 60자 이내다.
  - 정의 안에 "### 비유" 가 필요하다.
  - **접이식은 여섯 칸이 상한이다.** 정의·그림·정리·이해했는지·관련 용어를 뺀 나머지가
    일곱 개 이상이면 화면에 닿지 못하고 사라진다. 선택 섹션 4개를 다 쓰지 마라.
  - 코드 구현 섹션을 만들지 마라. 그 제목은 이제 오류다.
  - 같은 H2 제목을 두 번 쓰지 마라.

검사기는 **실패(✕)** 와 **경고(△)** 두 단계로 말한다. 실패는 반드시 고쳐야 하고,
경고는 "이게 맞나" 를 묻는 것이다. 경고를 그냥 넘기지 말고 한 번씩 판단해라 —
대부분은 `<` 를 `@` 로 바꾸거나 층을 흐름으로 바꾸라는 뜻이다.
`python3 tools/check_template.py --strict <파일>` 로 경고까지 실패로 세어 볼 수 있다.

**단, 네 가지 경고는 새 단어에서 실패로 취급된다.** `verify_new_terms.py` 가
`--require=examples,aim,loop,even` 으로 검사기를 부른다.

| 규칙 | 무엇을 어겼을 때 |
|---|---|
| `examples` | 💡 실제 사례가 `- **상황** — 설명` 이 아니다 |
| `aim` | 확인 질문에 `→ 답이 있는 자리` 가 없거나, 없는 자리를 가리킨다 |
| `loop` | `@` 가 흐름의 마지막 줄이 아니거나 여러 개다 |
| `even` | `\|=\|` 가 대조의 칸 이름 줄이 아닌 데 있다 |

넷 다 형식을 그대로 재는 규칙이라 제대로 쓰면 걸릴 일이 없다.
**이 자리들을 퀴즈가 직접 먹기 때문에** 조여 뒀다 — 실제 사례는 "이 상황은 어떤
개념인가" 문제가 되고, 확인 질문은 회상 화면이 답을 어디서 찾을지 알려주는 근거다.
형식이 어긋나면 앱에서 조용히 나쁜 문제가 만들어진다.

파일은 content/<위 목록의 폴더>/<단어>.md 로 만든다.

각 단어의 맨 아래에 참고한 출처를 남겨라. **H2 제목을 쓰지 마라** —
check_template.py 는 템플릿에 없는 H2 를 오류로 잡는다. `---` 아래 문단으로 쓴다:

    ---

    **출처**

    - https://... (문서 제목)
    - https://... (문서 제목)

build.py 의 clean_body 가 `---` 이후를 문서 푸터로 보고 잘라내므로, 이 목록은
저장소에는 남고 앱 화면에는 안 나간다. 출처는 나중에 검증할 사람을 위한 것이지
공부하는 사람에게 보여줄 것이 아니다.

### 6. 검증 — 통과 못 하면 커밋하지 않는다

    python3 tools/build.py
    python3 tools/verify_new_terms.py --expect 2

verify_new_terms.py 가 빌드 제외 0건, 단어 수 정확히 +2, 새 파일의 템플릿
통과를 한꺼번에 본다. 실패하면 메시지가 원인을 말해준다. 고치고 다시 돌려라.

그 다음, **네가 쓴 내용이 사실인지 스스로 다시 검사해라.** 집필할 때의 판단을
믿지 말고, 인용한 URL 을 다시 열어서 문장 하나하나가 그 문서에 실제로
있는 내용인지 대조해라. 확신이 안 서는 문장이 있으면 그 단어를 통째로 버려라.
애매한 것을 통과시키는 것보다 이번 주에 한 개만 넣는 편이 낫다.
(그럴 때는 --expect 를 실제 개수로 바꿔서 다시 검증해라.)

### 7. 실행 기록

logs/routine-<YYYY-MM-DD>-<전략>.md 를 만들어 다음을 적어라:
  - 후보로 검토한 단어와 고른 이유
  - 버린 단어와 버린 이유
  - 각 단어의 인용 출처 URL
  - 권별 단어 수 (1번에서 기록한 것)
  - 이번에 추가한 단어와 그 id
  - 이번 실행에서 이 문서나 도구가 틀렸다고 느낀 점 (있으면)

마지막 항목이 중요하다. 너는 이 도구들을 실제로 써 보는 유일한 자리에 있다.
지시가 검사기와 어긋나거나, 검사기가 잘못 통과시키거나, 문서가 낡았으면
적어 둬라. tools/ 를 직접 고치지는 말고 기록만 남긴다 — 사람이 읽고 고친다.

### 8. 커밋과 push

**순서가 중요하다.** 아래를 그대로 따라라.

    git add -A
    git commit -m "..."        # 커밋을 먼저 한다. 아래 설명 참조
    git pull --rebase
    python3 tools/build.py     # 리베이스로 남의 단어가 들어왔을 수 있으니 다시 굽는다
    git diff --quiet || (git add -A && git commit --amend --no-edit)
    git push

**커밋을 pull 보다 먼저 하는 이유.** 6단계에서 이미 build.py 를 돌렸으므로
data/index.js, data/terms/*.js, sw.js 가 수정된 상태다. 그 상태로 pull --rebase 를
부르면 git 이 거부한다 — `git add` 만 해도 마찬가지다:

    error: cannot pull with rebase: You have unstaged changes.
    error: cannot pull with rebase: Your index contains uncommitted changes.

작업트리가 깨끗해야 리베이스가 된다. 그래서 먼저 커밋하고, 리베이스한 뒤
다시 구워서, 달라진 게 있을 때만 그 커밋에 amend 로 접어 넣는다.

검증(6단계)은 커밋 전에 이미 끝났다. 여기서 다시 부르지 마라 —
verify_new_terms.py 는 HEAD 와 비교하는데 커밋 뒤에는 HEAD 가 이미 새 단어를
품고 있어서 +0 이 나온다.

리베이스에서 충돌이 나면 **직접 풀려고 하지 마라.** `git rebase --abort` 로
되돌리고, logs/ 에 충돌 사실만 적고 이번 실행을 끝내라. 다음 실행이 다시 한다.
자동으로 도는 자리에서 충돌 해결을 시도하는 것은 남의 단어를 지울 위험이 있다.

커밋 메시지는 무엇을 왜 넣었는지 한국어로 쓴다.

## 아무것도 못 넣었을 때

## 전략별 문단

### vocab-roadmap (월요일)

```
roadmap.sh 같은 확립된 개발자 커리큘럼을 기준으로, 12권 중 아직 없는
핵심 개념을 채운다. 기초에서 심화 순서로 간다.

후보가 비슷하게 좋으면 단어 수가 가장 적은 권을 우선한다. 분포는 여기 적어두지
않는다 — 적어두면 낡는다. 1번 단계의 `--dry-run` 결과에서 가장 얇은 권을 직접 봐라.

content/IT_Expert_로드맵.md 에 백로그가 있으나 일부는 이미 구현됐다.
반드시 실제 파일을 확인하고 골라라.
```

### vocab-trend (수요일)

```
최근 실무에 자리잡은 용어를 다룬다. 단, **공식 스펙이나 만든 조직의 공식
발표 문서가 있는 것만** 대상이다. 그런 문서가 없으면 아직 이 앱에 들어올
때가 아니다 — 유행어를 쌓지 않는 것이 이 루틴의 목적이다.

블로그와 뉴스에서 이름을 얻는 것은 괜찮지만, 인용은 반드시 공식 문서로 한다.
```

### vocab-related (금요일)

```
기존 단어의 "🔗 관련 용어" 에 나오는데 아직 자기 파일이 없는 단어를 채운다.

⚠️ 후보가 없을 수 있다. 한때 related 항목 전부가 기존 단어로 해소돼서 이 루틴이
할 일이 없었다. 세어 보고 판단해라 — 숫자를 미리 믿지 마라.

후보가 0개면 아무것도 만들지 마라. logs/ 에 "후보 없음" 만 적고 끝내라.
빈칸을 채우려고 즉흥으로 단어를 지어내지 마라.
```
